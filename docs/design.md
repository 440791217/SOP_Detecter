# 设计说明

## 职责

本服务接收浏览器上传的单帧，选择配置中的模型推理，返回原图坐标下的目标框、类别和置信度。Go 负责 RTSP 与 WebRTC，浏览器负责截帧和绘制，Java 负责业务权限、步骤规则与自动推进。第一版尚未修改现场页面和 Java 自动推进接口。

## 文件划分

| 文件 | 职责 |
|---|---|
| start.py | 直接运行的 Python 启动入口，在代码中指定配置文件路径 |
| app/main.py | 服务入口、生命周期、日志、跨域及请求体限制 |
| app/config.py | 严格解析 JSON 配置和默认参数 |
| app/api.py | 三个 HTTP 接口、鉴权、错误状态 |
| app/schemas.py | 请求上下文和检测结果结构 |
| app/models.py | 常驻模型注册、启动加载和预热、关闭释放 |
| app/predictor.py | 图片验证、串行推理、结果与耗时 |

文档在 `docs/`，模型在 `weights/`，所有日志在 `D:\projects\logs`。不增加 controller/service/repository 层。

## 生命周期和并发

服务启动时按照配置依次加载启用的模型，并用空白图片预热。每个模型每次启动仅加载一次，请求不能创建或下载模型。加载失败只将对应模型标记 unavailable，健康检查仍可访问，但该模型预测返回 503。

Uvicorn 单进程运行，不使用 reload 或多个 workers。每个 worker 会独立持有模型，因此默认启动入口禁止自动配置多进程。配置最多四个模型只是防止误配置，不代表 MX150 能同时容纳四个模型；当前只启用一个 nano 模型。权重和模型版本由管理员配置，修改后重启，无热切换。

所有模型共享一个非阻塞推理锁，覆盖图片解码到 GPU 结果回收；已有任务执行时，新预测返回 429，无推理排队。HTTP 上传解析仍可能发生在获取锁之前，但单个请求体有大小限制。推理在线程池执行，健康检查不会被 GPU 调用占住事件循环。浏览器也应保证每路最多一个在途请求，繁忙时丢弃旧帧，不重放积压图片。

## 输入与输出

仅接受 multipart JPEG/PNG 图片和 JSON metadata，不接受图片 URL、RTSP URL、本地文件路径或用户指定权重。文件默认最大 5MiB，总请求体限制为该值加 1MiB，解码像素上限 1600 万。输入按 EXIF 方向校正后转换 RGB；Ultralytics 缩放至模型输入尺寸，检测框回到校正后的原图像素坐标。前端用返回的宽高映射到视频显示区域，不能按固定 640 尺寸绘制。

所有上下文标识原样返回，不在服务中保存工位会话。空 detections 是有效识别结果，不等于步骤通过。服务不接受自动通过规则，也不伪造未加载模型的结果。

浏览器必须校验结果属于当前作业、步骤和帧；旧结果过期丢弃。最终自动推进还需要 Java 对当前执行状态、步骤顺序、规则、连续成功次数和幂等性进行校验。该逻辑不属于第一版检测服务。

## 日志和异常

运行日志、stdout、stderr、安装和测试日志统一在 `D:\projects\logs`，文件名前缀 `sop-detector-`。API 不保留输入图片和识别历史；上传解析器可能临时落盘，文件在请求结束关闭。输入正文、访问凭证不写日志。第三方模型设置文件放 `.cache/ultralytics`，不当作业务数据。

开发 Bearer 凭证默认 88888888；允许来源精确配置，不使用通配符。服务默认仅回环监听。当前开发凭证不等同于多用户业务授权，服务器多工位部署时还需部署者配置独立凭证、访问范围及容量。
